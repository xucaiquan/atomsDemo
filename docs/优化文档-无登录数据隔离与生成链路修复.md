## 0. 一句话结论

当前系统的**核心可用性已经打通**（异步受理避开 120s 网关超时、三阶段流水线、失败可读、沙箱预览、版本切换），但存在一条**最严重的全局性缺陷**：`routers/atoms.py` 全部 8 个接口都没有任何身份依赖，项目数据对所有访问者完全共享，`owner_key` 字段形同虚设（前端 `getOwnerKey()` **定义了但从未被调用**）。这不是「没做登录」的小问题，而是**任何匿名访客都能列出、读取、删除、并消耗模型配额改写他人项目**——按数据安全维度属于 P0。

其次是生成链路的**恢复能力粗糙**（只有单次空内容重试 + 截断续写，异常分类缺失、无退避、无超时），以及「同项目连续两轮增量」缺少**自动化回归证据**（当前仅 2 个纯函数测试文件）；版本回滚目前只是**前端查看**，没有后端语义，一旦要做回滚必然引出「回滚后下一轮从哪个版本续写」这个真实缺陷。

## 2. P0-1｜无登录情况下的全局数据共享与账号隔离【最高优先级】

### 2.1 问题（按严重度排序，全部有代码证据）

**问题 1：所有接口零鉴权，项目列表全局共享（致命）**

```python
# routers/atoms.py
@router.get("/projects")                     # ← 无 Depends(get_current_user)
async def list_projects(db=Depends(get_db)):
    result = await db.execute(select(Projects).order_by(Projects.updated_at.desc()))
    projects = list(result.scalars().all())   # ← 全库返回，无 owner 过滤
```

`atoms.py` 中 8 个接口（`list_projects:223`、`create_project:234`、`get_project:255`、`get_version:310`、`delete_project:336`、`generate:460`、`get_version_steps:538`、`cancel_generation:581`）**全部没有身份依赖、没有任何 owner 过滤**。后果：

- 任意匿名访客看到**全部用户**的项目与标题、需求原文、对话记录；
- 拿到 `public_id` 即可读**完整 HTML 源码**（`get_version` 是唯一返回 html 的接口，同样无鉴权）；
- 可 `DELETE /projects/{id}` 删除他人项目（级联删除版本/消息/步骤，不可恢复）；
- 可对他人项目 `POST /generate`：**消耗你的模型配额、并覆盖对方项目的 `latest_status`/标题**；
- `generate` 的并发约束也变成跨用户干扰面（他人可让你持续 409）。

**问题 2：`owner_key` 是"有字段无机制"**

- `data_models/projects.json:20-24` 定义了 `owner_key`（"浏览器会话标识，无账号体系下的归属键"）；
- `atoms.py:244` 在创建时写入：`owner_key=(data.owner_key or "")[:64] or None`，但**不校验、不查询、不返回**；
- `_project_brief`（`atoms.py:98`）**不返回 `owner_key`**，前端无法感知归属；
- 前端 `lib/constants.ts:19` 的 `getOwnerKey()` **全仓无任何调用点**（已 grep 验证），且它用 `localStorage` 生成 `anon-xxxx` —— 即使接上也是**客户端可任意伪造**的标识，不构成隔离。

**问题 3：归属键来自请求体，天然可伪造**

`CreateProjectRequest.owner_key` / `GenerateRequest.owner_key`（`atoms.py:79,84`）允许客户端自报身份。修复时**必须删除这两个字段**，改为服务端派生（见 §2.2 原则①）。

**问题 4：前端完全没有接平台现成的登录能力（能力浪费）**

平台已经具备完整认证设施，但本项目一个都没用：

| 平台已有 | 位置 | 本项目使用情况 |
|---|---|---|
| OIDC 登录/回调（PKCE） | `routers/auth.py:80`、`:107` | 未使用 |
| JWT 校验依赖 `get_current_user` | `dependencies/auth.py:27` | **atoms 路由未引用** |
| 平台用户表 `UserUpdate`/`UserResponse` | `schemas/auth.py` | 未使用 |
| 前端 `client.auth.me/toLogin/login/logout` | `skills_docs/web_sdk.md:22-30` | 未使用（`App.tsx` 甚至没有 `AuthProvider`） |
| `client.apiCall.invoke` 自动带凭证 | `skills_docs/web_sdk.md:11` | `atoms.ts` 用了 SDK，**后端不校验所以等于没带** |

同时仓库里存在**两套并存的认证代码**：`contexts/AuthContext.tsx` + `lib/auth.ts`（axios + `withCredentials`，走 `/api/v1/auth/me`）与平台推荐的 `client.auth.*`。`AuthContext` 未挂到 `App.tsx`（`App.tsx:27-28` 的 provider 槽位是空的），属于半成品，应二选一。

**问题 5：历史数据 owner 全为 NULL**

现有 `projects.owner_key` 均为 `None`。若直接加 `owner_key == 当前身份` 过滤，**所有既有项目会立刻对所有人消失**（含演示数据，`is_demo=true` 的 3 条 mock 数据）。

### 2.2 修复方案

#### 原则

1. **归属由服务端派生，绝不信任请求体。**
2. **一处实现、一处引用**：写一个依赖 + 一个过滤辅助函数，8 个路由逐一接上；不允许在路由里手写 `where`。
3. **默认拒绝（fail-closed）**：查不到归属一律 404（不是 403，避免探测项目是否存在）。

#### ① 身份解析依赖（新增）

```python
# dependencies/owner.py（新增文件）
async def get_owner_key(request: Request,
                        credentials=Depends(bearer_scheme)) -> str:
    """按优先级派生当前请求的归属键；匿名也必须拿到服务端签发的稳定标识。"""
    # 1) 平台登录用户：sub 优先
    if credentials:
        try:
            payload = decode_access_token(credentials.credentials)
            if payload.get("sub"):
                return f"user:{payload['sub']}"
        except AccessTokenError:
            pass                      # 落到匿名分支
    # 2) 匿名：读服务端 HMAC 签名的 HttpOnly cookie
    raw = request.cookies.get(ANON_COOKIE)   # atoms_anon
    if raw and _verify_anon(raw):
        return f"anon:{raw}"
    return ""   # 由调用方生成并 Set-Cookie（见 ②）
```

- 匿名标识必须是**服务端签名**（`HMAC-SHA256(secret, nonce)`，密钥复用 `settings.jwt_secret_key`），否则前端自造 `anon-xxx` 就等于没有隔离。
- cookie 属性：`HttpOnly; SameSite=Lax; Secure(生产); Max-Age=180d`。
- **关键动作**：在 `list_projects` / `create_project` 的响应里 `Set-Cookie`（这两个是入口，且必然被访问）。其他接口匿名 cookie 缺失时返回空归属 → 404，前端会被列表接口引导重新拿到 cookie。

#### ② 统一查询过滤（新增辅助）

```python
# routers/atoms.py
def _owned(stmt, owner: str):
    """所有项目域查询必须经过这里：唯一归属过滤入口。"""
    return stmt.where(Projects.owner_key == owner)

async def _fetch_owned_project(db, public_id: str, owner: str) -> Projects | None:
    result = await db.execute(
        _owned(select(Projects).where(Projects.public_id == public_id), owner)
    )
    return result.scalars().first()
```

然后**改造 8 处**（逐条列明，防漏）：

| # | 路由 | 改法 |
|---|---|---|
| 1 | `GET /projects` | `_owned(select(Projects), owner).order_by(...)`；`_recover_stale_versions` 必须**带 owner**（现签名只按 `public_id` 或全量，`atoms.py:152` 全量扫描会把别人的陈旧版本一起扫） |
| 2 | `POST /projects` | `owner_key=owner`；删除请求体的 `owner_key` |
| 3 | `GET /projects/{pid}` | 换成 `_fetch_owned_project` |
| 4 | `GET /projects/{pid}/versions/{seq}` | 先 `_fetch_owned_project`，再查版本；版本查询也加 `project_public_id` + 项目归属校验 |
| 5 | `DELETE /projects/{pid}` | 换成 `_fetch_owned_project` |
| 6 | `POST /projects/{pid}/generate` | 换成 `_fetch_owned_project`；删除请求体的 `owner_key` |
| 7 | `GET /projects/{pid}/versions/{seq}/steps` | 先校验项目归属 |
| 8 | `POST /projects/{pid}/versions/{seq}/cancel` | 先校验项目归属 |

另外 `_recover_stale_versions`（`atoms.py:152-195`）建议改为**只处理当前 owner 的项目**，避免匿名用户触发全库写操作（现在任意访客的一次列表请求就会全表扫描 + 可能全表 UPDATE 提交，属放大攻击面）。

#### ③ 历史数据迁移策略（必须显式决定，不能含糊）

推荐做法（三选一，需你确认，见 §8-Q3）：

- **方案 A（推荐）**：既有 `owner_key IS NULL` 的项目标记为 `is_demo=true` + 只读「演示项目」区，任何登录/匿名用户可见但**不可生成、不可删除**（后端对 `is_demo` 强制拒绝写操作）。演示链接的"首次打开列表不为空"（SC-006）得以保留，且不破坏隔离不变量。
- **方案 B**：一次性 `UPDATE projects SET owner_key='user:<你的平台ID>'`，把旧数据全部划归开发者账号。
- **方案 C**：演示环境直接清库重建（`is_demo` 种子脚本重跑）。

> 注意：不能既不迁移也不过滤——那等于保留当前的全局共享。

#### ④ 前端接线

由于 `atoms.ts` 已经用 `createClient()` + `client.apiCall.invoke`，**后端加上依赖后，登录用户自动带上 Bearer 凭证**，前端只需：

1. `App.tsx` 挂上认证状态（二选一后清理另一套）：
   - **推荐**：直接用 `client.auth.me()` 建立三态（`loading`/`authenticated`/`anonymous`）——符合 `skills_docs/web_sdk.md:61-63,73` 的强制要求，且 `AuthCallback.tsx` 是平台只读文件，必须配合 `client.auth.login()`；
   - 或者修好 `AuthContext` 并挂到 `App.tsx:27`，但 `lib/auth.ts:43` 依赖 `response.data.redirect_url`，与后端 `auth.py:100` 直接 302 的行为不一致（axios 跟随重定向会拿到 HTML），**这条路径当前是坏的**。
2. 顶栏加登录/登出入口（`pages/Index.tsx` header 区，`Index.tsx:358-374`），只在 `anonymous` 时显示「登录」按钮；**不要**用 `if (!user) navigate('/auth/callback')`（会无限循环）。
3. **登录/登出成功后必须清空并重载** `projects`/`detail`/`html`/`activeId`（`Index.tsx:69-114`）——否则登出后仍显示上一账号的项目列表，这是"看起来隔离了其实没隔离"的经典假象。
4. `lib/constants.ts` 的 `getOwnerKey()` **删除**（不要在修复里复活它）。

#### ⑤ 验收清单（A1/A2，必须有输出）

## 3. P0-2｜模型代码生成服务的稳定性与可恢复性（"修复后重新完成两类需求"）

### 3.1 问题（逐条对应代码）

**问题 1：失败分类粗，用户与运维都拿不到原因**

```python
# pipeline.py:309-318
except Exception as exc:
    logger.exception("生成流水线异常: %s", exc)
    message = "模型服务暂时不可用，请稍后重试"
    await self._fail(..., 3, message)
```

所有异常（401 密钥失效、429 限流、超时、502、代码 bug）都被压成**同一句**中文，且 `_call_step:494-496` 只把 `last_error` 作为 `__cause__` 留住、不区分类型。后果：无法判断"重试有用"还是"重试无用"；线上排障只能翻日志。

**问题 2：重试没有退避、没有超时**——`_call_step:481` 的 `for attempt in range(2)` 是紧贴重试；`AIHubService.gentxt`（`services/aihub.py:111-152`）把 `client.chat.completions.create` 交给 OpenAI SDK **默认超时**，一次卡住可能长时间占用流水线。

**问题 3：陈旧清理会误杀"仍然活着"的生成（真实竞态）**

```python
# atoms.py:166-176
created = version.created_at
if created and now - created < STALE_AFTER:   # STALE_AFTER = 10min（atoms.py:52）
    continue
version.status = "failed"                      # ← 无条件覆盖
```

流水线总耗时上限是 **3 次模型调用 × SDK 默认超时**，很可能超过 10 分钟；此时任意访客打开列表就把 `running` 版本置 `failed`，随后后台任务正常返回 `succeeded` 又被 `pipeline.py:329` 的守卫拦住（因为已不是 `ACTIVE_STATUSES`），最终用户看到**生成失败但内容其实已生成**。修法：改为基于 `versions.updated_at` 的**心跳**判定，并让 `_call_step` 在模型返回前定期刷新心跳。

**问题 4：整篇重跑路径代价高且会重复发送巨型 prompt**

`_generate_code:392-437`：attempt 2 重跑时仍用原 `user`（含 `previous_html` 全文）；而续写调用（`:415-427`）把 `user` + 完整 `doc` 作为 history 再发一次。多轮生成时 `doc` 可达数十 KB → 单次请求 token 翻倍，既贵又更容易超时截断。**需要给 `previous_html` 与 history 加上下文预算上限。**

**问题 5：`is_complete_document` 只认结尾，不认结构**

`html_extract.is_complete_document` 仅校验以 `</html>` 结尾。模型"续写时重开文档"的判定（`_DOC_RESTART_PATTERN`，`pipeline.py:44/431`）是 `match`（只匹配开头），若模型在开头输出一句解释再重开文档就会走 `_merge_continuation`，把两份文档拼起来——只要末尾恰好是 `</html>` 就**判定成功并入库**（脏数据）。需要补最小结构校验（`<html`、`</html>`、`<body>` 配对且不重复出现两个 `<!DOCTYPE`）。

### 3.2 修复方案（按优先级）

#### ① 错误分类与重试策略（新增 `services/aihub_errors.py` 的复用 + pipeline 分类）

| 上游症状 | 判定 | 策略 | 用户文案 |
|---|---|---|---|
| HTTP 401/403（密钥/权限） | 永久 | **不重试**，立即失败并打 ERROR 日志 | 「模型服务鉴权失败，请联系管理员」（避免让用户反复重试） |
| HTTP 429 | 可恢复 | 退避重试（0.5s→1s→2s，最多 3 次） | —（用户无感） |
| 超时 / 连接错误 / 5xx | 可恢复 | 退避重试（同 429） | —（用户无感） |
| 空内容（`content==""`） | 可恢复 | 现有单次重试 **+ 降低 `max_tokens` 再试一次**（思考链吃预算时更有效） | 「模型返回了空内容，请重新提交生成」 |
| 截断（无 `</html>`） | 走续写/重跑链（已有） | 见 ③ | 「生成的页面内容不完整（可能被截断）…」 |

实现要点：在 `_call_step` 里区分 `last_error` 的类型并抛出带 `retriable` 标记的 `PipelineError(message, step_seq, retriable=...)`；退避用 `await asyncio.sleep()`（注意：**取消接口的 `task.cancel()` 在 sleep 期间同样能生效**，不会破坏取消语义）。

#### ② 显式超时 + 心跳（解 §3.1 问题 3）

- `AIHubService.__init__`（`aihub.py:92`）显式传超时：`AsyncOpenAI(..., timeout=180.0, max_retries=1)`；或在 pipeline 侧用 `asyncio.wait_for(..., timeout=STAGE_TIMEOUT)` 包裹 `self._ai.gentxt(...)`，**超时按可重试处理**。
- 心跳：`_call_step` 在等待期间每 30s 执行一次 `UPDATE versions SET updated_at=now() WHERE ...`（`versions.updated_at` 由 ORM 自动维护，直接赋值即可），把 `_recover_stale_versions` 的判据从 `created_at` 改为 `updated_at`，`STALE_AFTER` 保持 10 分钟（前端 `GENERATION_POLL_TIMEOUT_MS=12min` 仍然覆盖）。
- 顺带收益：长任务不会被误判，也无需为了"防误杀"而放大 `STALE_AFTER`（放大反而让真实挂死的任务卡更久）。

#### ③ 上下文预算（解 §3.1 问题 4）

在 `services/prompts.py` 增加两个常量与截断函数，并在 pipeline 调用处统一使用：

```python
PREVIOUS_HTML_MAX_CHARS = 24_000   # 超出则保留 <head> + 前 N 字符 + 末尾 2000 字符，插入省略标记
CONTINUE_HISTORY_MAX_CHARS = 12_000  # 续写 history 里回传的 doc 上限（只回传尾部）
```

`build_code_user` 注入 `previous_html` 时必须过这个闸门；续写调用（`pipeline.py:421`）的 `history` 中 `content=doc` 改为只取尾部 `CONTINUE_HISTORY_MAX_CHARS`（续写只需要中断点附近上下文）。

#### ④ 结构完整性校验（解 §3.1 问题 5）

在 `services/html_extract.py` 增加 `looks_well_formed(doc) -> bool`（纯函数、易测）：至少满足 ① 恰好一个 `<!DOCTYPE`（若有）② `<html` 计数 == 1 ③ `<body` 计数 == 1 ④ 以 `</html>` 结尾。`_generate_code` 的"是否成功"判定从 `is_complete_document` 升级为 `is_complete_document and looks_well_formed`；同时 `_merge_continuation` 拼接后若出现两个 `<!DOCTYPE`/两个 `<body`，直接判定为"重开文档"并采用新产出（比正则 `match` 更鲁棒）。

#### ⑤ 失败可观测性（低成本高价值）

- `_fail` 写入的 `version.error` 保持用户可读文案，但把 `error_type`（`timeout`/`auth`/`rate_limit`/`truncated`/`empty`/`upstream_5xx`）与上游状态码写进 `versions.summary`（JSON 字段已存在，无需改模型）；
- `GET /versions/{seq}` 返回里可选加 `error_type`（前端不必展示，供排障）；
- 日志统一打 `project=<前8位> seq= model= stage= attempt= duration_ms=`，用于对齐"1~4 分钟"预期与定位慢阶段。

#### ⑥ 验收清单（A3）

用 Monkeypatch 注入 4 类故障（§5.3 给出 harness），期望：

| 注入 | 期望结果 | 期望不变量 |
|---|---|---|

## 4. P1-1｜两类需求 + 同项目连续两轮增量

### 4.1 现状与判定

- **需求类型 1（从零创建）**：`generate` → 无 `previous` → `previous_html=None`，`history_prompts` 为空 → 提示词不注入历史块（`test_context_memory.py:96-101` 已覆盖）。**逻辑正确。**
- **需求类型 2（迭代/指代）**：`atoms.py:496-518` 取"最新 succeeded 版本 HTML" + "本项目全部版本 prompt（升序）"，由 `prompts.build_history_block` 限 6 条 × 200 字，`ANAPHORA_HINT` 提示消解指代。**逻辑正确。**

那么"重做两类需求/两轮增量"的真正缺口不在实现，而在**没有回归证据**，以及下面 3 个**会真实咬人的边角缺陷**：

**缺陷 1：失败版本的 prompt 会污染历史**

```python
history_result = select(Versions.prompt).where(Versions.project_public_id == public_id)  # atoms.py:513
history_prompts = [row for row in history_result.scalars().all() if row]
```

**不过滤 `status='succeeded'`**。第一轮失败（比如"做一个贪吃蛇"截断失败），第二轮说"继续刚刚的需求"，历史里出现一条失败需求，模型可能把失败意图也当成需求延续。修法：`where(Versions.status == "succeeded")`（注意：**必须在 `prepare()` 落库新版本之前查询**，这一点现有注释已强调，改造时要保留）。

**缺陷 2：`HISTORY_ITEM_CHARS=200` 对"长需求 + 指代"太紧**

用户第一轮常是 500~1500 字的完整描述，截到 200 字后第二轮模型可能丢掉关键约束（例如"必须支持中文字体""不要用 CDN"）。建议：单条上限提到 400 字，且**最近 1 条不截断**（或截到 600 字），总预算仍在 `6 × 400 = 2400` 字量级，成本可控。

**缺陷 3：失败/取消轮次的 `previous_html` 语义**

`previous_html` 取的是"最新 succeeded"，这是对的；但**若该 succeeded 版本的 HTML 本身是脏数据（截断拼接产物）**，后续每一轮都会在此基础上"继承缺陷"。因此 §3.2④ 的结构校验不只是当轮的健壮性，也是**多轮演进质量的前置条件**——两轮增量的验收必须包含"第二轮不继承第一轮的脏结构"。

### 4.2 修复后必须产出的证据（A4/A5）

两轮增量的断言不能靠"看着对"，要断言**实际进入模型的内容**（§5.4 harness 用捕获的 prompt 做断言）：

```
轮次1 输入：「做一个记账小工具，能记收入和支出，显示总余额」
  断言：user 消息不含「需求历史」，不含「上一版页面」
  断言：版本 seq=1，status=succeeded，html 以 </html> 结尾

轮次2 输入：「继续刚刚的需求，再加一个按月份筛选的图表」（指代型短句）
  断言：user 消息 含「需求历史」且含「记账小工具」（消解成功）
  断言：user 消息 含「需求历史」条数 == 1（失败的轮次不入历史）
  断言：user 消息 含「上一版页面」且含轮次1 HTML 的特征串（如函数名/文案）
  断言：版本 seq=2，status=succeeded
  断言：seq=2 的 HTML 长度 ≥ seq=1 × 0.8（不是推倒重来）
  断言：prompt 总字符数 ≤ 预算上限（防上下文线性膨胀）
```

补充两个**并发/顺序**用例（当前完全无测试）：

- 生成中再次提交 → `409 CONFLICT`（`atoms.py:487-494`），且**不产生新版本记录**（`prepare` 未被调用）；
- 取消后立刻重新提交 → 新版本 `seq+1`，被取消版本的 `prompt` **不进入**下一次历史（配合缺陷 1 修复）。

## 5. P1-2｜版本回滚 + 源码/Preview 一致性

### 5.1 版本回滚：当前只有"查看"，没有"回滚"

**现状**：`VersionSwitcher.tsx` 只是切换查看（`Index.tsx:117-134` 的 `switchVersion`），后端**没有**任何 restore/rollback 接口。这符合原始 US3"旧版本保留可切换"，但用户说的"版本回滚"显然期望更强语义。

**关键设计缺陷（一旦实现回滚必然暴露）**：`atoms.py:497-507` 的续写基线永远是"**seq 最大**的 succeeded 版本"。若用户回滚到 v2 然后说"在这个基础上再改"，系统会拿 **v5** 作为 `previous_html` —— 回滚形同虚设。这是必须在设计阶段就定死的问题。

**方案（推荐"回滚即新版本"，不动数据模型）**：

```
POST /api/v1/atoms/projects/{public_id}/versions/{seq}/restore
  前置：项目归属校验；目标版本存在、status=succeeded、html 非空（否则 409 "该版本没有可回滚的内容"）
  行为：创建 seq' = max(seq)+1 的新版本，
        html/prompt 复制自目标版本，summary 追加 {"restored_from": seq}，
        status='succeeded'，duration_ms=null，并写一条 assistant message「已回滚到 v{seq}」
  返回：{"restored": true, "version_seq": seq', "restored_from": seq}
```

- **不销毁历史**：v3/v4/v5 仍在，可再次回滚，符合"不可变版本链"直觉；
- **让基线选择自然正确**：因为回滚产生了新的最大 seq，下一轮增量自动以它为基础，**无需改 pipeline 的基线逻辑**（这是选此方案的主要原因）；
- 与并发约束一致：存在 `pending/running` 版本时返回 409（复用现有检查）；
- 前端：`VersionSwitcher` 上加"回滚到此版本"（二次确认），成功后 `setActiveSeq(新seq)`、重载详情与 HTML、`toast.success`。

**若你更倾向"指针式回滚"**（不产生新版本，只标记 current）：那必须新增 `projects.current_version_seq` 列，并把 §4.1 的基线查询、历史查询全部改成 `seq <= current_version_seq`。**代价明显更大，且回滚不再可审计**，不推荐。

**验收（A6）**：

| 步骤 | 期望 |
|---|---|
| v1 记账 → v2 加月份筛选 → 回滚到 v1 | 产生 v3；v3.html 与 v1.html **逐字节相等**（注意：两者都已含注入后的 CSP，应一致） |
| 检查 v2 | 仍存在、仍 `succeeded`、仍可切换查看 |
| 回滚后提交「在现在的基础上再加导出」 | 新版本 v4 的 `previous_html` **等于 v3.html**（不是 v2），断言"回滚后基线正确" |
| 对 `status=failed` 的版本回滚 | 409 + 可读中文，无新版本产生 |
| 回归：对 v1 连续回滚两次 | v3、v4 内容相同（幂等语义清晰） |

### 5.2 源码 / Preview 一致性

**好消息**：两个视图**共用一个 `html` 状态**（`Index.tsx:64`），`PreviewPane` 用 `srcDoc={html}`（`PreviewPane.tsx:63`），`CodeViewer` 用 `html.split('\n')`（`CodeViewer.tsx:39`）——所以**不存在"两个请求各拿一份"的结构性不一致**，也不需要为一致性额外请求。真正的不一致来自**过渡态与渲染语义**：

**问题 1：切换版本失败时保留旧内容（最可能的用户可见不一致）**

```typescript
// Index.tsx:117-134 switchVersion
setActiveSeq(seq);                      // ← 立即高亮新版本
try { const full = await atomsApi.getVersion(activeId, seq); setHtml(full.html || ''); }
catch (e) { toast.error(...); }         // ← html 仍是上一个版本！
```

失败或慢响应期间，标签高亮 v3 而预览/源码显示 v2 —— 这就是"源码与 Preview 不一致"的真实形态。修法：进入切换时 `setHtml('')` 并置 `versionLoading=true`（用现有 `detailLoading` 或新增），渲染骨架/错误态，**不允许在加载中展示旧 HTML**。

**问题 2：CSP 注入导致"源码 ≠ 生成产物"**

`pipeline._generate_code` 返回的是 `inject_csp(doc)`（`pipeline.py:408/436`），即**入库的 HTML 已含 CSP meta**。因此"源码视图"展示的是**注入后**的最终产物，这一点是正确的（所见即所运行）；但需要显式确认：若 `inject_csp` 重复调用会产生**两个 CSP meta**，第二个的 `default-src 'none'` 可能覆盖更宽松的策略。请在 `html_extract.inject_csp` 与回滚路径上确认**幂等**（已存在则不重复注入），并加一个单元测试。

**问题 3：无"这是哪一版"的可核验标识**

建议在预览工具条（`PreviewPane.tsx:52-58`）与代码工具条（`CodeViewer.tsx:61-73`）都显示 **版本号 + 长度 + 短哈希**（如 `v3 · 42.1KB · sha256:9f2c…`）。这样"一致性"从"肉眼比对"变成**可断言**：两处数字必须相同，且等于 `GET /versions/{seq}` 返回的 `html` 的哈希。前后端各加一个纯函数即可（前端 WebCrypto/`length`+`djb2` 都行）。

**问题 4：失败版本的空 HTML 与旧版本残留**

`switchVersion` 对 `failed` 版本会 `setHtml(full.html || '')` → 空 → `PreviewPane` 显示空提示，同时 `setFailedMessage(full.error)`（`Index.tsx:125`）——行为正确，但**提示区在输入框附近**（`Index.tsx:440-444`），与预览区距离远，容易误读为"预览坏了"。建议在预览区同步展示失败原因条。

**验收（A7）**：

1. 同一版本切换 `preview`/`code`：显示的版本号、字符数、哈希三者一致；
2. 快速连续点击 v1→v2→v3：任意时刻不出现"高亮 v3 而内容为 v1"（用网络节流 3s 复现，修复后应显示加载态）；
3. 回滚到 v1 后：预览内容 == v1 内容 == 源码内容 == 哈希一致；
4. `GET /versions/{seq}.html` 与页面源码视图 `html` **逐字节相等**（在前端加一个开发态断言或测试脚本比对）。
