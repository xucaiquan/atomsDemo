## 1. 阻断级问题（P0）

### 1.1 `owner.py` 的哈希身份修复被合并丢弃 → 跨用户数据可见

`app/backend/dependencies/owner.py` 当前实现：

```python
return OwnerContext(owner_key=f"user:{sub}"[:64], anon_key=None)
```

`_SUBJECT_CHARS=32` 常量、`_warned_missing_secret` 告警、以及 `_user_key()`（用 `sha256(subject)[:32]`，总长 37）**全部丢失**。

**后果**：两个共享 ≥59 字符前缀的长 `sub` 会截断到同一个 `owner_key`，两个不同用户看到彼此的项目。

**为什么没有被数据库挡住**：`models/projects.py` 是 `owner_key: Mapped[Optional[str]] = mapped_column(String(64), nullable=True)`，`data_models/projects.json` 的 `maxLength` 也是 64 —— 截断到 64 是「合法写入」，DB 层不会报错。

**证据**：
```
git merge-base --is-ancestor d53420b HEAD   → YES
git diff d53420b HEAD -- app/backend/dependencies/owner.py  → 修复被回退
```

> **【已修复 · T019（实现）+ T015（回归测试）】** `owner.py` 恢复 `_user_key()`：
> `"user:" + sha256(subject).hexdigest()[:32]`（总长 37 < 64），截断碰撞消除。
> 探测这一条的正是 `test_distinct_long_subjects_yield_distinct_keys`
> （三个前缀相同的长 `sub` 必须产出三个不同归属键），见 1.4。

### 1.2 硬编码兜底密钥 → 匿名身份可伪造

```python

```

这是公开仓库里的常量。若部署环境未设 `JWT_SECRET_KEY`，任何人可以离线签出合法匿名 cookie/header。同时 d53420b 中「空密钥时告警一次」的逻辑也被丢弃，导致该危险配置**静默生效**。

> **【部分修复 · T003】——如实记录，不是已修复。**
> 已恢复的是**告警**：`_warned_missing_secret` 让「未设 `JWT_SECRET_KEY`」在首次
> 触发时打印一次显式警告，该危险配置不再静默。
> **但 `_FALLBACK_SECRET = "atoms-studio-anon-fallback-key"` 仍然存在于
> `app/backend/dependencies/owner.py:39`**——提交 2 的原始方案（缺失密钥时**拒绝
> 签发**而非回退到公开常量）没有落地。在部署环境补齐 `JWT_SECRET_KEY` 之前，
> 匿名身份依然可离线伪造。这是本报告中**唯一一条未按方案修复的 P0 项**。
>
> 当前代码把「降级」写成刻意选择（`owner.py:55`：「宁可匿名身份可伪造，也不能让

> 告警」，二者不等价——告警只让运维可能发现，拒绝签发才真正消除可伪造性。

## 2. 生成流水线（用户报的核心问题）

### 2.1 阶段3是主导故障点

隔离探针（`probe_upstream.py`，用与线上完全相同的 prompt 构造）：

| 阶段 | 模型 | max_tokens | 结果 |
|------|------|-----------|------|
| stage1 | `deepseek-v4-flash` | 4096 | HTTP 200，**4.0s** |
| stage2 | `deepseek-v4-flash` | 4096 | HTTP 200，**9.8s** |
| stage3 | `deepseek-v4-pro` | 16384 | **HTTP 524（网关超时），126.2s** |

成功那次完整流水线 `step3 = 203.96s`（step1 9.05s、step2 19.89s，总 238.6s）。**阶段3就贴在上游网关的断点附近**——203.96s 成功与 126.2s 被 524 切断只差一次运气。

> **【已修复（短期方案）· T003】** `STAGE_TIMEOUT` 由 240.0 降为 **120.0**，取在
> 上游实测 126.2s 返回 524 的切断点**之内**，不再为一个已被切断的请求白等。
> 中期方向（流式/分块生成，把单次调用压进 126s）**未做**——见 §8「仍未完成项」。
> 该项的上游侧结论（阶段3 仍是瓶颈、`deepseek-v4-pro` + 16384 tokens）本应随
> T037 的探针重跑复核，当前因未部署而顺延。

### 2.2 重试是「乘法」，没有整体预算

`_generate_code` 的恢复链：

```python
for attempt in range(2):                          # 2 轮
    code_raw = await self._call_step(...)         # 最坏 3 × 240s = 720s
    for round_no in range(2):                     # 每轮 2 次续写
        cont_raw = await self._call_step(...)     # 各最坏 3 × 240s = 720s
```

最坏 = `2 × (720 + 2×720)` = **4320s = 72 分钟**，中间没有任何整体阶段预算。

> **【已修复 · T003/T004/T005】** 三条同时落地：
> - `GENERATION_BUDGET_SECONDS = 420.0`，流水线入口取 `deadline = monotonic() + 420`
>   （单调时钟，不受系统时间调整影响）；
> - `MAX_ATTEMPTS` 由 3 降为 **2**、`RETRY_BACKOFF_SECONDS` 由 `(0.5,1.0,2.0)`
>   改为 `(0.5,1.0)`；
> - 每次调用前按 `min(STAGE_TIMEOUT, max(remaining, MIN_CALL_BUDGET_SECONDS))` 取等待
>   上限，阶段**入口**若剩余预算低于 `MIN_CALL_BUDGET_SECONDS = 5.0` 则不再发起调用，
>   直接以 `error_type="budget_exhausted"` 落库（T005）。
>
> 于是最坏耗时从 4320s 收敛为**有界的 420s**，且恒小于 `STALE_AFTER`（600s）。
> 实测见 `tests/test_budget_exhaustion.py`（T027）。

### 2.3 心跳让 stale 回收永久失效

- `_heartbeat` 每 30s 用独立会话刷 `versions.updated_at`
- `_recover_stale_versions` 的判据正是 `version.updated_at or version.created_at`，`STALE_AFTER = 10min`

**只要后台任务还活着（哪怕毫无进展），`updated_at` 就一直是新的 → 回收永不触发。** 心跳证明了「进程活着」，但被当成了「任务有进展」。

> **【已修复 · T006】** `_heartbeat` 与 `HEARTBEAT_INTERVAL` **已删除**，原处留下
> 「**不得以任何形式复活**」的确认结论（`services/pipeline.py:566`）：
> `versions.updated_at` 只在真实进展点（`_finish_step` 写摘要、`_fail` 写终态）推进，
> `_call_step` 把步骤置 `running` 时改的是 `generation_steps` 行，**不**推进版本行。
> 由此活任务最长静默期 = 阶段3 预算 420s < `STALE_AFTER` 600s，
> 回收判据才重新成立。另有回归哨兵 `test_heartbeat_is_gone`
> （`tests/test_time_budget_invariants.py`）从类属性层面挡住复活，
> 以及 `test_stale_recovery.py` 中替代 `test_heartbeat_refreshes_updated_at` 的新用例。

### 2.6 失败落库不完整，且错误归因错误

另一次线上失败（项目 `8abf5ac5-eece-4362-9c16-05530b479c2e`），45.8s 即失败：

```
steps = ['succeeded', 'running', 'failed']
error_type = unknown
summary    = {"step1": "...", "error_type": "unknown"}
```

**没有 `attempts`，没有 `upstream_status`。**

推理：`_call_step` 抛 `PipelineError` 时**必定**带 `attempts`；只有 `_run_stages` 的通用兜底才只传 `error_type` 且**硬编码 `step_seq=3`**：

```python
except Exception as exc:  # noqa: BLE001 - 兜底为可读中文提示
    logger.exception("生成流水线异常: %s", exc)
    await self._fail(project_public_id, version_seq, 3, message, error_type="unknown")
```

所以异常是**从 `_call_step` 之外逃逸**的。`_call_step` 里以下语句都在重试 `try` 之外：

```python
version = await self._get_version(...)          # 在 try 外
step    = await self._get_step(...)             # 在 try 外
await self._db.commit()                         # 在 try 外
request = GenTxtRequest(...)                    # 在 try 外 ← 构造失败会直接逃逸
```

后果有两层：(a) 错误被归因到**从未启动的 step3**；(b) **step2 被留在 `running`**。

**确切的异常类型需要服务端日志才能定论——这是诚实的未知，不应猜。**

> **【已修复 · T026/T031/T032 + T028】** 四条一起处置：
> - **归因**：`_run_stages` 的通用 `except Exception` 不再硬编码 `step_seq=3`，
>   改用 `_call_step` 进入时记录的自有状态（`_current_step_seq`），失败落在
>   **流水线实际所在阶段**；`summary` 里补记**异常类名**（`exception=type(exc).__name__`）
>   保留可观测性，也顺带回答本节那句「诚实的未知」——以后可从落库记录读到类型。
> - **新增 `attempts`**：`_current_attempts` 一并落库。**这里查出一个真实缺陷**：
>   `budget_exhausted` 这条路径原先**漏传 `attempts`**，导致「根本没试（0 次）」与
>   「试过但失败了」在失败记录里无法区分——由 T027 的红→绿暴露并修掉
>   （FR-013「失败记录必须完整可区分」）。
> - **残留 `running`**：`_fail` 增加收尾清扫，把该版本下仍 `running` 的步骤一并置

### P1 — 用户报的核心问题

5. **给阶段3加整体预算**。在 `_generate_code` 外层包 `asyncio.wait_for`（如 `CODE_STAGE_BUDGET = 420s`），把 72 分钟的最坏情况压成有界。
   **→ ✅ 已解决（方案有调整）· T004/T005**（回归：T027）
   落地形式**不是**「仅包阶段3 的 `wait_for`」，而是**整条流水线共享一份 420s 预算**：
   `deadline = monotonic() + GENERATION_BUDGET_SECONDS`，每次调用取
   `min(STAGE_TIMEOUT, max(remaining, MIN_CALL_BUDGET_SECONDS))`，阶段入口再按剩余
   预算决定是否放行。三点差异值得记录：
   - **更严**：原方案只界住阶段3 是自己 420s，叠上前两阶段仍可到 ~460s；整条
     共享预算后**总耗时**才真正 ≤420s，也才保证「< STALE_AFTER(600)」。
   - **不用 `wait_for` 包一层**：由每次调用的超时上限收缩来兑现截止，
     少一层取消语义（`wait_for` 的取消会与「取消是状态优先」的既有设计交互）。
   - **阶段3 的可用预算被前两阶段挤压**——这是刻意的取舍：宁可整体有界，
     也不让单阶段无限膨胀。

## 7. 会话侧发现（本轮新增）

复核聚焦生成流水线，会话/身份侧只做了顺带验证。以下三条是**本轮新增的发现**，
其中两条在修复中才成形，属于「复核没问到、但不修就是坏的」范围。

### 7.1 匿名 cookie 的 `Secure` 属性必须由请求的实际 scheme 推导（T020）

原实现没有给匿名 cookie 设 `Secure`——生产（HTTPS）下这等于让身份 cookie 走明文
信道传输。但**写死 `Secure` 同样是坏的**：本地开发与测试跑在 `http://` 上，
浏览器不会回传带 `Secure` 的 cookie，于是匿名身份每请求重建，表现为
「刚建好项目，紧接着就 404」。这条不是理论风险——**`ANON_COOKIE_SECURE='1'`
曾一次性让 28 个用例失败**（`tests/test_owner_dependency.py` 里有记录）。

落地方式：`_json()` 按请求实际 scheme 推导（`https` → 带 `Secure`），
并提供 `ANON_COOKIE_SECURE` 环境变量覆盖，应对网关未传 `X-Forwarded-Proto`
的情形。**安全属性不得由被保护方指定**：直连 TLS 优先，伪造
`X-Forwarded-Proto: http` 不能把 HTTPS 请求降级成非 `Secure`（有用例专门守住）。
回归测试：`tests/test_owner_dependency.py` 的 cookie 传输属性组（T018）。

### 7.2 登出必须由服务端做，前端清 localStorage 不算登出（T021/T022）

匿名 cookie 是 **`HttpOnly`** 的（刻意如此，防 XSS 窃取身份），前端 JS
**原理上读不到也删不掉**。旧实现里前端 `clearAnonKey()` 只清得掉 localStorage，
cookie 原样留着，下一次请求又回到旧匿名身份——用户看到的现象是
**「登出无效，还是能看到刚才的东西」**。

落地方式：新增 `POST /api/v1/atoms/session/logout`（T021），服务端签发一个
**全新匿名身份**，经 `Set-Cookie` 与响应体两条通道一并下发。
一处刻意的选择：**不调 `response.delete_cookie()`**——同 name + 同 path 的
`set_cookie` 本身就覆盖旧值，而多写一条 `Set-Cookie` 会引入顺序陷阱
（浏览器按顺序应用同名 cookie，删除那条若排在写入之后，刚签发的新身份会被立刻抹掉）。
需要的是「换成新身份」，不是「先清空」。

前端侧（T022）：`clearAnonKey` 的语义边界被写进注释——**它不是登出**，
保留它是给「登录态切换」用的（登录身份优先级高于匿名身份）。
`atomsApi.logout()` 的顺序有意为「**先清本地、再发请求**」：即便请求失败，
请求头通道也不会继续携带旧标识；此时 cookie 通道仍归服务端管，属已知边界。
回归测试：`tests/test_session_logout.py`（T017）断言新 `anon_key` ≠ 旧值、
双通道下发、**携新身份看不到旧身份的项目**、连续调用幂等。

### 7.3 刷新后回到上次打开的项目（T023/T024）

复核时 `activeId` 初值为 `null`，刷新即回到空工作区。现按 `LAST_PROJECT_KEY`
（`atoms_last_project`）恢复上次项目，并补齐**进行中生成自动接回**：
刷新时若存在 `pending`/`running` 版本则自动恢复 2.5s 轮询直至终态，
用户无需重新提交（FR-027）。

两处刻意的约束：**只存 `public_id`，不存项目内容**——内容必须重新从服务端取，
避免拿本地副本冒充服务端状态；**归属校验仍在服务端**——恢复时若该 id 不属于
当前身份（换了身份、登出后又刷新），详情请求会 404，前端静默丢弃。
切换/打开项目时清除旧 `html`，避免闪现上一个项目的内容。
