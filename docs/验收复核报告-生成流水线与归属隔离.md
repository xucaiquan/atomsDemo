## 1. 阻断级问题（P0）

### 1.1 `owner.py` 的哈希身份修复被合并丢弃 → 跨用户数据可见

`app/backend/dependencies/owner.py` 当前实现：

```python
return OwnerContext(owner_key=f"user:{sub}"[:64], anon_key=None)
```

`_SUBJECT_CHARS=32` 常量、`_warned_missing_secret` 告警、以及 `_user_key()`（用 `sha256(subject)[:32]`，总长 37）**全部丢失**。

**后果**：两个共享 ≥59 字符前缀的长 `sub` 会截断到同一个 `owner_key`，两个不同用户看到彼此的项目。

**为什么没有被数据库挡住**：`models/projects.py` 是 `owner_key: Mapped[Optional[str]] = mapped_column(String(64), nullable=True)`，`data_models/projects.json` 的 `maxLength` 也是 64 —— 截断到 64 是「合法写入」，DB 层不会报错。

**证据**：
```
git merge-base --is-ancestor d53420b HEAD   → YES
git diff d53420b HEAD -- app/backend/dependencies/owner.py  → 修复被回退
```

### 1.2 硬编码兜底密钥 → 匿名身份可伪造

```python
_FALLBACK_SECRET = "atoms-studio-anon-fallback-key"
```

这是公开仓库里的常量。若部署环境未设 `JWT_SECRET_KEY`，任何人可以离线签出合法匿名 cookie/header。同时 d53420b 中「空密钥时告警一次」的逻辑也被丢弃，导致该危险配置**静默生效**。

### 1.3 `_verify` 对 `None` 会崩

```python
def _verify(raw: str) -> Optional[str]:
    parts = raw.split(".")      # raw 为 None → AttributeError → 500
```

且 `sig` 只校验长度 16，未做十六进制形状校验。

### 1.4 合并事故导致测试基线为红

```

```

- `FAILED tests/test_owner_dependency.py` ×4（`test_verify_rejects_client_made_key`、`test_verify_rejects_non_canonical_shape`、`test_distinct_long_subjects_yield_distinct_keys`、`test_missing_secret_warns_once`）

## 2. 生成流水线（用户报的核心问题）

### 2.1 阶段3是主导故障点

隔离探针（`probe_upstream.py`，用与线上完全相同的 prompt 构造）：

| 阶段 | 模型 | max_tokens | 结果 |
|------|------|-----------|------|
| stage1 | `deepseek-v4-flash` | 4096 | HTTP 200，**4.0s** |
| stage2 | `deepseek-v4-flash` | 4096 | HTTP 200，**9.8s** |
| stage3 | `deepseek-v4-pro` | 16384 | **HTTP 524（网关超时），126.2s** |

成功那次完整流水线 `step3 = 203.96s`（step1 9.05s、step2 19.89s，总 238.6s）。**阶段3就贴在上游网关的断点附近**——203.96s 成功与 126.2s 被 524 切断只差一次运气。

### 2.2 重试是「乘法」，没有整体预算

`_generate_code` 的恢复链：

```python
for attempt in range(2):                          # 2 轮
    code_raw = await self._call_step(...)         # 最坏 3 × 240s = 720s
    for round_no in range(2):                     # 每轮 2 次续写
        cont_raw = await self._call_step(...)     # 各最坏 3 × 240s = 720s
```

最坏 = `2 × (720 + 2×720)` = **4320s = 72 分钟**，中间没有任何整体阶段预算。

### 2.3 心跳让 stale 回收永久失效

- `_heartbeat` 每 30s 用独立会话刷 `versions.updated_at`
- `_recover_stale_versions` 的判据正是 `version.updated_at or version.created_at`，`STALE_AFTER = 10min`

**只要后台任务还活着（哪怕毫无进展），`updated_at` 就一直是新的 → 回收永不触发。** 心跳证明了「进程活着」，但被当成了「任务有进展」。

### 2.4 前端轮询的端点不做回收 → UI 永远「生成中」

| 路由 | 是否调用 `_recover_stale_versions` |
|------|-----------------------------------|
| `GET /projects` (363) | ✅ |
| `GET /projects/{id}` (412) | ✅ |
| `POST .../generate` (674) | ✅ |
| `POST .../restore` (876) | ✅ |
| **`GET .../versions/{seq}/steps` (737)** | ❌ **前端每 2.5s 轮询的就是这个** |

任务死掉后，用户盯着轮询界面会**一直**看到「生成中」，除非手动切到项目列表/详情页。

而且版本长期 `running` 会占住「一个项目同时只有一个活跃生成」的名额 → 同项目再次 `generate` 返回 **409 CONFLICT** → 项目在用户看来「卡死」。

### 2.5 线上实测复现（本轮）

项目 `879518ea-68c8-4dbf-8e62-ab7c2ab9580e` 第二轮增量：

```
step1 需求分析  succeeded  22.5s
step2 结构设计  succeeded  22.9s
step3 代码生成  running    >14.7 分钟  ← 无终态
探针在 424.6s 放弃（status=TIMEOUT）
```

调用 `GET /projects/{pid}`（会触发回收）之后：

```
v2 status = failed
error     = 生成过程被中断（服务重启或连接断开），你的描述已保留，可重新提交
error_type= None        ← 回收路径不写 error_type
```

**即：后台任务实际已死，但版本在 `running` 上挂了 14.7 分钟，只因为我恰好调用了会触发回收的端点才落库为 `failed`。**

时间关系也是错的：

```
STAGE_TIMEOUT(240s) × MAX_ATTEMPTS(3) = 720s  ==  前端 GENERATION_POLL_TIMEOUT_MS = 12 分钟
后端最坏 4320s = 72 分钟  >  前端 12 分钟
```

**单阶段的超时预算就已经等于前端的全部轮询预算**，多层叠加后差距是 6 倍。

### 2.6 失败落库不完整，且错误归因错误

另一次线上失败（项目 `8abf5ac5-eece-4362-9c16-05530b479c2e`），45.8s 即失败：

```
steps = ['succeeded', 'running', 'failed']
error_type = unknown
summary    = {"step1": "...", "error_type": "unknown"}
```

**没有 `attempts`，没有 `upstream_status`。**

推理：`_call_step` 抛 `PipelineError` 时**必定**带 `attempts`；只有 `_run_stages` 的通用兜底才只传 `error_type` 且**硬编码 `step_seq=3`**：

```python
except Exception as exc:  # noqa: BLE001 - 兜底为可读中文提示
    logger.exception("生成流水线异常: %s", exc)
    await self._fail(project_public_id, version_seq, 3, message, error_type="unknown")
```

所以异常是**从 `_call_step` 之外逃逸**的。`_call_step` 里以下语句都在重试 `try` 之外：

```python
version = await self._get_version(...)          # 在 try 外
step    = await self._get_step(...)             # 在 try 外
await self._db.commit()                         # 在 try 外
request = GenTxtRequest(...)                    # 在 try 外 ← 构造失败会直接逃逸
```

后果有两层：(a) 错误被归因到**从未启动的 step3**；(b) **step2 被留在 `running`**。

**确切的异常类型需要服务端日志才能定论——这是诚实的未知，不应猜。**

### 2.7 `AsyncOpenAI` 未显式设置超时与重试

`services/aihub.py` 的构造没有 `timeout`，也没有 `max_retries`。设计文档 §3.2② 明确要求 `AsyncOpenAI(..., timeout=180.0, max_retries=1)`，未落地。默认值会与 `STAGE_TIMEOUT` 叠加，让实际等待时间不可预测。

### 2.8 已排除的假设

`generation_steps.output` 列过窄 —— **不成立**。`models/generation_steps.py` 是 `mapped_column(String, nullable=True)`（无限长），实测 step2 输出被 API 截断在 2000 字符（列表端点的展示截断），列本身正常。

## 5. 优化方案

### P0 — 正确性与安全，立即

1. **恢复 `owner.py` 的哈希身份**：`_user_key()` 用 `sha256(subject)[:32]`（总长 37，远小于 64），消除截断碰撞。恢复 `_SUBJECT_CHARS` 常量。
2. **拆掉 `_FALLBACK_SECRET`**：`JWT_SECRET_KEY` 缺失时应**拒绝签发**匿名身份并启动告警，而不是回退到公开常量。
3. **加固 `_verify`**：先判 `None`/非字符串，再校验 `sig` 的十六进制形状。
4. **修复合并事故**：让 8 个红测试转绿——它们正是 1.1 的回归探测器，必须先绿。

### P1 — 用户报的核心问题

5. **给阶段3加整体预算**。在 `_generate_code` 外层包 `asyncio.wait_for`（如 `CODE_STAGE_BUDGET = 420s`），把 72 分钟的最坏情况压成有界。
6. **重新对齐超时三层关系**。当前 `240×3 = 720s` 恰好等于前端 12 分钟，是设计缺陷。建议：`STAGE_TIMEOUT = 120s`（贴近上游 524 实际断点 126s）、`MAX_ATTEMPTS = 2`，续写轮次由整体预算裁剪。不变量：**后端最坏耗时 < 前端轮询上限**。
7. **`AsyncOpenAI(timeout=…, max_retries=…)` 显式化**（设计文档 §3.2② 已写，未落地）。
8. **让轮询端点也能回收**：给 `GET /versions/{seq}/steps` 加 `_recover_stale_versions`。
9. **把心跳从「存活」改成「进展」语义**。当前心跳无条件刷 `updated_at`，等于废掉 stale 回收。建议引入 `deadline_at` 硬截止字段，超时**无条件**回收，不依赖心跳；或心跳只基于「最后一次真实进展」刷新。
10. **修通用兜底**：`except Exception` 必须带真实 `step_seq`（当前硬编码 3 导致错误归因），并把异常信息落库；同时保证异常逃逸时不会把已完成阶段的步骤留在 `running`。

### P2 — 可观测性

11. **失败落库补齐** `attempts` / `upstream_status` / 真实 `step_seq`；stale 回收路径也要写 `error_type`（当前为 `None`）。
12. **让线上日志可取**：`logger.exception` 已记录，但复核过程中无法获取服务端 traceback，导致 2.6 只能停在推理。
13. **前端区分两种终态**：「轮询超时」（我不知道后端怎样了）与「后端失败」（后端明确告诉我失败了）不该显示同一种文案。

### P3 — 验收补齐

14. 按 §3 表格补测试，优先级：`/cancel` 端到端（需要非 `GENERATION_INLINE` 的后台任务路径）> A5 的长度比与裁剪门限断言 > A3 的 5xx 端到端注入 > A7 的 E2E。
15. 新建 `docs/验收证据/` 存放 E2E 证据。
16. 修正 `test_generation_inline.py` 中与 `conftest.py` 事实矛盾的 docstring 前提。

### 关于阶段3本身

阶段3的 524 是**上游网关在 126s 切断**，而我们的单次调用预算 240s 和它不匹配。中期方向：**流式生成或分块生成**，把单次调用压到 126s 以内；短期至少让 `STAGE_TIMEOUT` 低于 126s，避免为一个已被切断的请求白等。
