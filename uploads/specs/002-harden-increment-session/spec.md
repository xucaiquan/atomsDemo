# Feature Specification: 增量可靠性与会话连续性加固

**Feature Branch**: `002-harden-increment-session`

**Created**: 2026-09-21

**Status**: Draft

**Input**: 用户描述："为 Atoms Studio 设计优化方案：修复「同项目两轮增量 + 旧功能保留」与「新会话恢复」两项验收在线上无法通过的问题。目标：让这两项验收能在线上稳定通过，并把失败变成用户可理解、可重试、可观测的终态。"

## 背景与定位

本特性的出发点是一次**线上验收复核**（2026-09-21，对 `https://keegan.pub.atoms.world`）。复核结论是：这两项验收之所以「不通过」，**不是功能没实现，而是实现缺少时间预算与终态保证**。

已实测复现的核心事实：

- 三阶段生成中，前两阶段稳定在 18–23 秒，**第三阶段（代码产出）是唯一瓶颈**，实测在 126 秒、204 秒、996 秒以上之间剧烈波动，三次复测**全部卡在第三阶段**无法在可接受时间内到达终态。
- 当前实现里第三阶段最坏可占用约 **72 分钟**，而用户界面只等待 **12 分钟**。也就是说：界面对用户说「超时了」，服务端还在继续消耗额度——用户永远看不到真实结果，也拿不到可理解的失败原因。
- 版本会停在「进行中」长达 **14.7 分钟**无终态。原因是**存活信号被当成了进展信号**：系统每 30 秒无条件续期一次"我还在跑"，而超时回收恰好以这个续期时间为判据，于是「只要进程活着就永远回收不了」。
- 用户界面在等待期间所查询的那个接口，**恰好是唯一不具备回收能力的接口**。所以即使后台任务已经死亡，界面也会无限显示「生成中」。
- 一次真实失败留下的记录**没有尝试次数、没有上游状态**，且**被归因到了一个从未启动的阶段**，同时把已经完成的阶段错误地留在「进行中」。
- 「新会话恢复」的**主通道本身是好的**（刷新后数据仍在、跨身份隔离正确、伪造标识被拒），但其外围存在三处缺口：传输保护标志缺失、登出后浏览器侧身份痕迹清不干净、刷新后不恢复"上次打开的项目"。

因此本特性的目标是三件事：**给生成一个与用户等待预算对齐的硬时间上限**、**让每一个"进行中"都必然走向一个可理解、可重试、可观测的终态**、**把会话恢复从"能恢复"补到"干净地恢复"**。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 在已有项目上追加需求，旧功能必须还在 (Priority: P1)

用户先让平台做了一个计算器。用了一会儿之后，他回到同一个项目，说「继续刚刚的需求，再加一个历史记录区域，能回看最近几次计算」。他期望的是**在原来那个计算器上加东西**，而不是拿到一个陌生的新应用——原来能加减乘除、能清除、能看显示屏，加完之后这些都还得在。

**Why this priority**: 这是产品的核心价值主张「在同一次对话里把想法长成产品」的直接体现。如果第二轮会推倒重来、或者根本跑不完，产品就退化成「一次性生成玩具」，用户不敢在上面做真实投入。这一条不成立，其余都不重要。

**Independent Test**: 在空白处创建一个项目并生成第一轮，随后对同一项目提交一句指代型追加需求（如「继续刚刚的需求，再加一个 X」），观察两轮是否都在可接受时间内到达终态，并逐项核对第一轮已实现的能力在第二轮产物中是否仍然存在。此测试不依赖登录、回滚、会话恢复等任何其他功能。

**Acceptance Scenarios**:

1. **Given** 一个已成功生成过一轮的项目, **When** 用户提交一句指代型追加需求, **Then** 系统在可接受时间内产出一个新版本，且该版本**保留了第一轮版本的全部既有能力**
2. **Given** 追加需求提交后生成仍在进行, **When** 用户持续观察进展, **Then** 用户在最坏情况下也能在一个明确的上限时间内拿到终态（成功或失败），不会无限期等待
3. **Given** 第一轮版本已成功, **When** 第二轮生成成功, **Then** 第一轮版本的内容与校验指纹**逐字节保持不变**，仍然可以原样回看
4. **Given** 追加需求使用了「继续刚刚的需求」「按之前说的」这类指代, **When** 系统解析需求, **Then** 指代被正确地还原为第一轮的具体上下文，而不是被当成一个孤立的新需求

---

### User Story 2 - 刷新之后，回到我原来的地方 (Priority: P2)

用户正在等一次生成，或者刚看完一个满意的版本，顺手刷新了页面（或关掉标签页第二天再打开）。他期望：**我还是我**，项目列表里我的东西都还在，点进去应用原样重现，如果刚才那次生成还在跑，界面应该**自动接回**继续显示进展，而不是假装什么都没发生。

**Why this priority**: 无登录体系下，「我是谁」完全依赖浏览器侧的持久化痕迹。这条一旦有裂缝，用户会直接看到「我的项目不见了」——这是最伤信任的一类故障。它排第二是因为它不阻断主流程，但它是"数据还在吗"的信任底线。

**Independent Test**: 创建一个项目并生成，随后**完全丢弃内存状态**（模拟刷新/新标签页）重新访问，仅依赖浏览器侧持久化的身份痕迹，验证项目列表、版本、页面内容与校验指纹是否与刷新前一致；再换一个全新身份访问，验证看不到任何他人项目。

**Acceptance Scenarios**:

1. **Given** 用户已创建项目并生成过版本, **When** 用户刷新页面（仅凭浏览器侧持久化痕迹）, **Then** 项目列表、历史版本、页面内容与校验指纹与刷新前**完全一致**
2. **Given** 用户提交的生成仍在进行中, **When** 用户刷新页面, **Then** 界面自动接回并继续显示该次生成的进展，直到终态，用户无需重新提交
3. **Given** 用户在一个全新浏览器（无任何持久化痕迹）中访问, **When** 加载项目列表, **Then** 看不到任何其他用户创建的项目
4. **Given** 用户处于登录状态, **When** 用户登出, **Then** 浏览器侧不再残留任何能被后续请求带上的上一身份痕迹

---

### User Story 3 - 失败必须说清楚，并且让我能重来 (Priority: P3)

生成失败时，用户看到的应该是「哪一步失败了、是暂时性还是配置性、我能不能直接重试」，而不是一句笼统的「服务暂时不可用」，更不是永远转圈的「生成中」。而且失败之后，他应该能**立刻**再提交一次，而不是被告知「该项目已有生成在进行中」。

**Why this priority**: 失败本身不可怕，不可理解的失败和卡死才可怕。它排第三是因为它不改变功能可达性，但决定了用户遇到问题时是"重试一下"还是"放弃这个产品"。

**Independent Test**: 注入各类失败（暂时性限流、上游服务错误、鉴权失效、产出被截断、空产出），验证每一种都在上限时间内落到明确终态，记录中包含失败阶段、失败类型与尝试次数，且失败归因指向真实失败的阶段；随后立即再次提交，验证不被拒绝。

**Acceptance Scenarios**:

1. **Given** 上游连续返回暂时性错误, **When** 重试次数耗尽, **Then** 版本落到失败终态，记录中包含失败阶段、失败类型与尝试次数
2. **Given** 上游返回鉴权类错误, **When** 系统识别到该错误不可通过重试恢复, **Then** 立即失败，不做无谓重试，且给出可区分的说明
3. **Given** 一次生成因异常中断, **When** 用户查看该版本, **Then** 失败被归因到**真实失败的阶段**，且不存在任何被留在「进行中」的已完成阶段
4. **Given** 某项目的一次生成已卡死并被回收, **When** 用户在该项目上再次提交生成, **Then** 提交被正常受理，不被拒绝
5. **Given** 用户看到失败, **When** 用户重新提交同一段描述, **Then** 原描述仍然保留，用户不需要重新输入

---

### Edge Cases

- **产出被截断**：模型返回的页面不完整（缺少收尾结构）。系统应先尝试接着写，仍不完整再整篇重做；所有恢复动作都必须计入同一个时间上限，**不得因为"还在努力"而无界延长**。
- **产出为空**：模型返回空内容。系统应能以不同参数重试，最终必须落到明确终态，不得静默产出空页面。
- **两轮之间版本被判失败**：失败轮次的描述**不得**污染后续轮次的上下文，后续轮次的增量基线必须仍是最近一个**成功**的版本。
- **第二轮比第一轮短**：追加需求后产物显著变小通常意味着「推倒重来」而非「增量」，应被视为可疑并需要人工/自动核对旧功能保留。
- **等待期间界面放弃**：界面放弃等待**不等于**后端停止工作。必须保证二者有明确的先后关系：后端上限 < 界面等待上限，否则用户永远看不到真实结果。
- **进程重启**：后台任务随进程消失时，正在进行中的版本必须在有限时间内被回收为可读失败，且用户描述不丢失。
- **同一项目并发提交**：应被拒绝（避免互相覆盖），但**卡死回收后必须能立刻再次提交**。
- **身份标识被篡改**：客户端携带的伪造标识必须被拒绝并回落到新签发，不得读到他人数据。
- **标识长度边界**：两个长度很长、前缀相同的账号标识**不得**被折叠成同一个归属键。
- **登出后返回**：登出后重新请求不得带出上一身份可见的数据。
- **跨设备**：匿名身份以浏览器为边界，跨设备不延续（属于产品已知边界，见 Assumptions）。

## Requirements *(mandatory)*

### Functional Requirements

**增量与旧功能保留**

- **FR-001**: 系统 MUST 支持在同一项目上连续多轮追加需求，每轮产出独立新版本，历史版本不被覆盖
- **FR-002**: 每一轮增量 MUST 以**最近一个成功版本**的页面作为增量基线；失败或被取消的版本 MUST NOT 成为后续轮次的基线
- **FR-003**: 每一轮增量的需求上下文 MUST 包含该项目此前**成功版本**的需求描述
- **FR-004**: 系统 MUST 能解析「继续刚刚的需求」「按之前说的」这类指代，将其还原为具体历史上下文，而非当作孤立新需求
- **FR-005**: 需求上下文的体积 MUST 有上限，不得随轮次线性增长
- **FR-006**: 第二轮及以后的产物 MUST 保留此前版本已实现的能力；验收 MUST 在**产物层面**核对，而非仅断言注入内容

**时间预算与终态**

- **FR-007**: 一次生成（从接受到终态）MUST 有一个**整体时间上限**，该上限对所有重试与恢复动作**整体生效**，而非逐次生效
- **FR-008**: 该整体上限 MUST 严格小于用户界面的等待上限，二者关系 MUST 有单一的、可校验的定义
- **FR-009**: 任何版本 MUST 在整体上限内落到终态（成功 / 失败 / 已取消），MUST NOT 无限期停留在「进行中」
- **FR-010**: 「进行中」的回收 MUST 由**硬性截止**触发，MUST NOT 依赖"进程是否存活"这一类存活信号
- **FR-011**: 用户界面在等待期间所查询的接口 MUST 同样具备回收能力，使界面不会永久显示「进行中」
- **FR-012**: 上游调用的等待上限 MUST 被显式声明，MUST NOT 依赖上游客户端库的默认值

**失败落库与归因**

- **FR-013**: 失败 MUST 记录：失败阶段、失败类型、尝试次数、上游状态（可得时）
- **FR-014**: 失败 MUST 被归因到**真实失败的阶段**；MUST NOT 归因到未启动的阶段
- **FR-015**: 一次失败 MUST NOT 把已完成的阶段留在「进行中」
- **FR-016**: 系统 MUST 区分**可通过重试恢复**与**不可通过重试恢复**的错误，后者立即失败
- **FR-017**: 面向用户的失败说明 MUST 可理解、不包含堆栈或内部路径，并给出重试入口
- **FR-018**: 生成失败或被回收后，该项目 MUST 能立即再次接受生成请求
- **FR-019**: 用户提交的描述在该次生成失败后 MUST 保留

**会话与身份连续性**

- **FR-020**: 在无登录体系下，用户的身份 MUST 仅由服务端派生；请求体中的任何字段 MUST NOT 影响归属
- **FR-021**: 用户的身份标识 MUST 经**签名保护**，客户端伪造的标识 MUST 被拒绝并回落为新签发
- **FR-022**: 用户身份的持久化 MUST 具备**双通道**（自动携带通道 + 显式携带通道），避免单一通道被网关吞掉后身份静默失效
- **FR-023**: 生产环境的身份标识 MUST 仅通过受保护通道传输
- **FR-024**: 归属键 MUST 在不同账号之间唯一，MUST NOT 因标识长度限制而被截断合并
- **FR-025**: 登出 MUST 清除浏览器侧全部上一身份痕迹，包括自动携带通道
- **FR-026**: 刷新或重新打开后，用户 MUST 能看见自己的全部项目与历史版本，内容与校验指纹与刷新前一致
- **FR-027**: 刷新时若存在进行中的生成，界面 MUST 自动接回该次生成的进展直至终态
- **FR-028**: 全新身份 MUST NOT 看到任何其他用户创建的项目（演示项目除外，见 Assumptions）
- **FR-029**: 任一身份 MUST NOT 能读取、修改或删除他人项目（含直接按标识访问）

**验收证据**

- **FR-030**: 「两轮增量 + 旧功能保留」MUST 有端到端证据，且包含**产物级**的旧功能逐项核对
- **FR-031**: 「刷新后恢复」MUST 有端到端证据，覆盖自动携带通道与显式携带通道两条路径
- **FR-032**: 「取消」MUST 有真实执行路径的端到端证据，而非仅在模拟环境中断言状态边界
- **FR-033**: 「源码 / 预览一致」MUST 有独立于产出方自述的验证手段，不得仅用同一算法复算同一份数据自证
- **FR-034**: 上下文体积上限相关的约束 MUST 有对应测试覆盖
- **FR-035**: 仓库测试基线 MUST 为全绿；当前已知的红灯 MUST 被修复或明确废弃

### Key Entities *(include if feature involves data)*

- **项目**：用户的创作单元，归属由服务端派生的归属键决定；存在「演示项目」这一对所有访客可见的特殊类别。
- **版本**：项目下的一次生成产出，具有单调递增的序号、终态（成功 / 失败 / 已取消）、页面内容及其校验指纹、失败说明。
- **生成步骤**：一次生成内部的阶段序列，各自具有终态与耗时；失败归因必须指向真实阶段。
- **需求历史**：该项目此前成功版本的需求描述，按序供后续轮次解析指代使用，体积有上限。
- **增量基线**：最近一个成功版本的页面内容，作为下一轮增量的起点。
- **身份标识**：服务端派生的归属依据，匿名形态为带签名的不可伪造标识，经双通道在浏览器侧持久化。
- **整体时间上限**：一次生成从接受到终态的硬性截止，与界面等待上限构成单一可校验的先后关系。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 连续两轮增量在 **95%** 的尝试中于 **4 分钟**内两轮均到达终态；**100%** 在 **8 分钟**内到达终态（成功或明确失败）
- **SC-002**: 第二轮产物对其第一轮已实现能力的**保留率 100%**（逐项核对，允许新增，不允许丢失）
- **SC-003**: **0** 个版本停留在「进行中」超过整体上限；超过上限即被回收为可读失败
- **SC-004**: **100%** 的失败记录包含失败阶段、失败类型与尝试次数
- **SC-005**: 失败归因错误率 **0**（不存在指向未启动阶段的失败，不存在已成功阶段被留在「进行中」）
- **SC-006**: 生成失败或被回收后，**1 次提交内**即可再次生成（**0** 次因卡死导致的持续拒绝）
- **SC-007**: 刷新后 **100%** 能看见自己的项目与历史版本，页面内容与校验指纹与刷新前**逐字节一致**
- **SC-008**: 全新身份看到他人项目 **0 次**；任一身份越权访问他人项目成功 **0 次**
- **SC-009**: 登出后，后续请求中可携带的上一身份痕迹残留 **0 处**
- **SC-010**: 平台自身的等待上限与用户界面等待上限的关系 **100%** 满足「平台先于界面给出终态」
- **SC-011**: 仓库测试基线 **0 失败 0 错误**
- **SC-012**: 第 1、2、3 项用户故事各自具备**独立可复跑的端到端证据**，且证据中包含产物级核对结果

## Assumptions

- **上游代码产出天然慢且波动大**：实测单次代码产出在 126 秒（上游网关切断）到 996 秒以上之间波动。因此平台**必须自设预算**，不能把时间控制权交给上游。
- **平台网关存在约 120 秒的读超时**：这决定了生成必须保持「异步受理 + 轮询」的语义，不得改为同步等待。
- **匿名身份以浏览器为边界**：跨设备/跨浏览器不延续身份，属于已知产品边界，不在本特性范围内。
- **演示项目对所有访客可见**是既有的产品设计，不算越权。
- **无登录体系不引入账号合并**：匿名身份与登录身份的数据不自动合并，属于既有设计决定。
- **上游模型可替换**：本特性不假设某个具体模型永远可用；时间预算与终态保证必须对模型替换保持有效。
- **改动范围受平台模板约束**：平台受保护目录（框架核心、生成的数据模型、入口文件）不可修改；路由前缀、错误信封格式等既有契约保持不变。
- **不新增用户表**：用户管理由平台内建能力承担。

## Out of Scope

- 跨设备/跨浏览器的身份延续
- 匿名身份与登录身份的数据自动迁移或合并
- 上游模型本身的速度优化（如改为流式或分块产出）——本特性只要求平台侧具备与之无关的预算与终态保证
- 生成产物的视觉质量与功能正确性本身
