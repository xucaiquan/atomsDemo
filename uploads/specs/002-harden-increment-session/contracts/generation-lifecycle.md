# Contract: 生成生命周期

**Feature**: `002-harden-increment-session` | **Date**: 2026-09-21

本契约定义**一次生成从受理到终态**的完整责任链，以及每条时间约束。它是本特性最核心的契约——复核发现的所有生产故障最终都可归因于这份责任链上"有一段时间没人负责"。

## 生命周期

```text
T0  受理                     routers/atoms.py::generate
    ├─ 校验归属与冲突        （409 若已有活跃版本）
    ├─ 落库 pending 版本 + 3 个 pending 步骤 + 用户消息
    ├─ commit
    └─ 返回 202 {version_seq}          ← 必须毫秒级（契约 C-1）

T1  后台任务启动              services/pipeline.py::run
    ├─ 计算 deadline = start + GENERATION_BUDGET_SECONDS      ← 本特性新增
    └─ 注册进 _RUNNING_TASKS

T2  阶段执行（1 → 2 → 3）
    每个阶段：
    ├─ remaining = deadline - now                             ← 本特性新增
    ├─ 若 remaining 低于最小可用预算 → 不再发起调用，落库"预算耗尽"
    ├─ 置步骤 running + commit（短事务，不跨越 AI 调用）
    ├─ 调用上游，超时 = min(STAGE_TIMEOUT, remaining)          ← 本特性新增
    └─ 写步骤产出 + 推进 versions.updated_at（真实进展点）

T3  终态落库（五条路径，互斥）
    ├─ succeeded        流水线
    ├─ failed           流水线（上游/截断/预算/内部）
    ├─ cancelled        取消接口（状态优先）
    ├─ failed           通用兜底（内部异常逃逸）
    └─ 上述全部受 ACTIVE_STATUSES 守卫保护

T4  释放资源
    ├─ 移出 _RUNNING_TASKS
    └─ 项目恢复可提交（契约 C-4）

T5  兜底回收（仅当 T2~T4 未能发生——进程死亡 / 任务消失）
    └─ 由 list / detail / generate / restore / steps 端点惰性触发
       判据：running 且 updated_at 超过 STALE_AFTER
```

## 时间约束（必须成立的不等式）

```text
单次调用上限        STAGE_TIMEOUT              = 120s
整条流水线上限      GENERATION_BUDGET_SECONDS  = 420s
回收阈值            STALE_AFTER                = 600s
前端等待上限        FRONTEND_POLL_TIMEOUT      = 720s

                    120 < 420 < 600 < 720
```

**每条不等式的含义**

| 不等式 | 含义 | 违反后果 |
|---|---|---|
| `120 < 420` | 单次调用必须能在预算内至少完成一次并留有恢复余地 | 预算被单次调用吃光，任何恢复都不可能 |
| `420 < 600` | 活任务的最长静默期必须短于回收阈值 | **活任务被误杀**——这正是心跳当初要解决的问题 |
| `600 < 720` | 回收必须早于前端放弃 | **用户永远等不到真实终态**——这正是当前生产的表现 |

> `STAGE_TIMEOUT = 120` 还额外受上游行为约束：实测上游网关在 **126.2s** 处返回 524，因此单次等待设在其内侧，避免为已被上游丢弃的请求白等。

## 责任矩阵

| 故障情形 | 谁写终态 | 时限 | 用户看到 |
|---|---|---|---|
| 正常完成 | 流水线 | ≤ 420s | 页面 |
| 上游持续失败 | 流水线 | ≤ 420s | 可读失败 + 重试入口 |
| 上游鉴权失败 | 流水线（立即，不重试） | 秒级 | 可区分的失败说明 |
| 产出截断且恢复失败 | 流水线 | ≤ 420s | 可读失败 |
| 超出整体预算 | 流水线（主动止损） | = 420s | "超出时间预算，描述已保留" |
| 用户取消 | 取消接口 | 即时 | 已取消，旧版本不受影响 |
| 内部异常逃逸 | 流水线通用兜底 | 即时 | 可读失败（归因到真实阶段） |
| **进程死亡 / 任务消失** | **回收路径（惰性）** | ≤ 600s | 可读失败 |

**核心断言**：前七行覆盖**所有进程存活的情形**，且全部在 420s 内。回收路径只负责最后一行的"进程不在了"。当前实现的问题在于把第二到七行也一并押在了回收路径上。

## 失败归因契约

任何失败必须满足：

1. **真实阶段**：`failed_seq` 指向实际失败的阶段；不得指向未启动的阶段。
2. **无残留运行**：该版本下不得存在仍为 `running` 的步骤；已完成阶段保持 `succeeded`。
3. **字段完整**：`error_type` 非空；`attempts` 在适用时非空；`upstream_status` 在可得时非空。
4. **页面为空**：失败版本的 `html` 为空——宁可无页面，不可有静默半成品。
5. **描述保留**：`prompt` 保留，用户无需重新输入。

## 取消契约

1. **状态优先**：先写 `cancelled`（版本 + 活跃步骤 + 项目）并 `commit`，**之后**才取消任务。
2. **晚到结果不得覆盖**：所有写入路径以 `if version.status in ACTIVE_STATUSES` 守卫；含**预算超时**这一新路径。
3. **阶段边界检查**：上一阶段执行期间被取消时，不得发起下一阶段的调用。
4. **可测试**：必须存在一条**真实后台任务**的取消路径测试（非 INLINE 模式），证明路由与任务取消都被走到（spec FR-032）。

## 增量契约

1. **基线**：每轮增量以上一轮**成功**版本的页面为基线；失败/取消版本不得成为基线。
2. **历史**：需求上下文只含**成功**版本；失败轮次不得污染后续（既有测试已覆盖，属回归红线）。
3. **预算**：上下文体积有上限，不随轮次线性增长。
4. **产物级保留**：第二轮产物必须保留第一轮已实现能力——**必须在产物层核对**，仅断言注入内容不算通过（spec FR-006/FR-030）。

## 会话契约

1. 身份仅由服务端派生（JWT > 签名 cookie > 请求头 > 新签发）。
2. 双通道下发，避免单一通道被网关吞掉后身份静默失效。
3. 生产 cookie 必须含 `Secure`。
4. 登出必须清除浏览器侧全部上一身份痕迹（含 `HttpOnly` cookie，只能由服务端下发）。
5. 归属键长度无关地唯一。
6. 刷新后：项目、版本、页面内容与摘要与刷新前逐字节一致；进行中的生成自动接回。
