# Feature Specification: 智能体驱动的应用生成平台（Atoms Demo）

**Feature Branch**: `001-atoms-demo`

**Created**: 2026-09-15

**Status**: Draft

**Input**: 用户描述："完成一个可运行的 Atoms Demo：实现一个可运行的网页应用，具备类似 Atoms 的能力与 UI 交互体验，即通过智能体驱动的方式完成代码（应用）生成，并将生成的应用以可视化网页形式进行展示。"

## 背景与定位

这不是一个业务应用，而是一个**平台型产品原型**：用户用自然语言描述想要的软件，系统由智能体驱动完成代码生成，并把生成结果以可视化网页的形式当场呈现给用户。

核心价值主张：**把"想法"到"可交互的产品"之间的距离压缩到一次对话**。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 一句话生成可运行的应用 (Priority: P1)

访问者打开平台，看到一个输入框。他输入"帮我做一个记账小工具，能记收入和支出，显示总余额"，提交后，页面在一分钟内渲染出一个**可以真实点击、真实输入**的记账应用——他可以立刻在里面记一笔账，看到余额变化。

**Why this priority**: 这是产品的全部意义所在。没有这条链路，产品不存在。其余所有故事都建立在它之上。

**Independent Test**: 在空白页输入一段应用描述并提交，能观察到生成的应用被渲染出来，且可与之交互（输入、点击产生真实反馈）。此测试不依赖历史记录、迭代、过程可视化等任何其他功能。

**Acceptance Scenarios**:

1. **Given** 用户停留在初始页面且输入框为空, **When** 用户输入一段有效的应用描述并提交, **Then** 系统开始生成，并在生成完成后将结果渲染为可交互的应用界面
2. **Given** 生成已完成, **When** 用户与渲染出的应用交互（如填写表单、点击按钮）, **Then** 应用产生真实的界面反馈，而非静态图片或占位内容
3. **Given** 用户提交了描述, **When** 生成尚在进行中, **Then** 用户在提交后 3 秒内看到明确的进展反馈，且界面不会呈现无响应的空白状态

---

### User Story 2 - 生成结果被保存，随时可以回来 (Priority: P2)

用户生成了一个应用，关掉标签页，第二天想起来再看看。他重新打开平台，**昨天的项目还在列表里**，点进去，应用原样重现，连他上次的对话记录都在。

**Why this priority**: 原始需求明确把"数据持久化"列为硬性要求。没有持久化，产品只是一次性的玩具，且会被判定为"概念验证（PoC）"而非"实际可用的功能"。

**Independent Test**: 生成一个应用 → 关闭页面/重启服务 → 重新打开平台 → 确认项目、生成结果与对话记录均可完整找回。

**Acceptance Scenarios**:

1. **Given** 用户已成功生成至少一个应用, **When** 用户刷新页面或重新打开平台, **Then** 之前生成的项目出现在项目列表中，且内容与生成时一致
2. **Given** 用户在项目列表中, **When** 用户选择一个历史项目, **Then** 系统展示该项目的完整内容，包括其生成结果与对话记录
3. **Given** 平台服务被重启, **When** 用户重新访问, **Then** 已有数据仍然完好，不出现丢失

---

### User Story 3 - 在已有结果上继续提要求 (Priority: P3)

用户对生成的记账工具基本满意，但想加一个"按月筛选"的功能。他不重新描述一遍，而是直接说"再加一个按月份筛选的图表"，系统在**原有基础上**改进，产出一个新版本，原版本仍然保留。

**Why this priority**: 这是从"玩具"到"工具"的分水岭——真实的产品迭代就是这样发生的。同时它天然带出"版本"这一数据结构，回滚能力近乎免费获得。

**Independent Test**: 对一个已有项目追加一次修改要求，确认产生新版本且旧版本仍可访问。

**Acceptance Scenarios**:

1. **Given** 用户已有一个生成完成的项目, **When** 用户在该项目下追加一条修改要求, **Then** 系统产出更新后的生成结果，且其中包含原应用已有的功能（不推倒重来）
2. **Given** 一个项目已有两次以上的生成记录, **When** 用户查看该项目的版本列表, **Then** 用户能看到历次版本，并可切换到任意历史版本查看

---

### User Story 4 - 看见智能体在工作 (Priority: P4)

用户提交描述后，界面上出现一条**分步骤的工作流**："理解需求 → 设计结构 → 生成代码"，每一步实时从"等待"变为"进行中"再变为"已完成"，甚至能看到智能体当前的思考片段。用户不再是盯着一个转圈的加载图标干等，而是**看着一个团队在为他干活**。

**Why this priority**: 原始需求的核心措辞是"**智能体驱动**"。这个可视化是产品与"一次性代码生成器"之间的体验分水岭，也是评估维度中"创新性"的主要得分点。它不承担功能正确性，但承担体验差异。

**Independent Test**: 提交一次描述，确认界面上出现了分步骤的状态展示，且各步骤状态随生成进程真实推进。

**Acceptance Scenarios**:

1. **Given** 用户提交了一段描述, **When** 生成过程进行中, **Then** 界面上出现多个有序的步骤项，其状态随实际进程推进而更新
2. **Given** 生成过程中某一步骤正在进行, **When** 该步骤完成, **Then** 界面在无需用户刷新的情况下反映最新状态

---

### Edge Cases

- 用户提交**空白描述**或纯符号、无实际含义的内容时，系统如何响应？
- 用户的描述**超出平台能力边界**（例如"做一个淘宝"）时，系统如何回应而非默默失败？
- 生成的代码存在**语法错误或运行时报错**，导致无法渲染时，系统是否给出可理解的提示并保留本次生成记录？
- 生成过程**耗时过长或中途中断**（网络波动、服务异常）时，用户输入的内容与已有项目是否安全？
- 生成的应用**尝试访问外部网络、读取宿主页面数据或执行危险操作**时，系统如何隔离？
- 用户在生成进行中**重复点击提交**时，系统如何处理？
- 生成结果**体积过大**导致渲染卡顿时，系统如何应对？
- 用户输入包含**非中文/中英混杂**的描述时，系统是否同样可用？

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 用户 MUST 能以自然语言描述期望的应用，并获得一份可运行的生成结果
- **FR-002**: 系统 MUST 将生成结果以可视化网页形式呈现，用户 MUST 能直接与之交互（输入、点击等产生真实反馈）
- **FR-003**: 系统 MUST 在生成过程中持续输出进展反馈；自用户提交起 **3 秒内** MUST 出现首个可见反馈，界面 MUST NOT 呈现无响应的空白状态
- **FR-004**: 系统 MUST 将每个项目及其生成结果持久化存储；用户刷新页面或服务重启后 MUST 能完整找回
- **FR-005**: 用户 MUST 能查看自己的历史项目列表
- **FR-006**: 用户 MUST 能在既有项目上追加修改要求，系统 MUST 基于原有结果产出更新版本，而非重新开始
- **FR-007**: 系统 MUST 保留同一项目的历次生成版本，用户 MUST 能查看并切换到任一历史版本
- **FR-008**: 系统 MUST 在界面上展示生成过程的阶段性步骤，各步骤状态 MUST 随实际进程实时更新
- **FR-009**: 用户 MUST 能查看生成结果对应的源代码
- **FR-010**: 系统 MUST 在**隔离的执行环境**中渲染生成结果，使其无法读取或修改平台自身的数据、凭据与页面上下文
- **FR-011**: 当生成失败、超时或返回无效结果时，系统 MUST 给出用户可理解的错误提示，且 MUST NOT 丢失用户已输入的描述与已有项目数据
- **FR-012**: 系统 MUST 对同一用户的重复/并发生成请求加以约束，避免重复消耗与资源争抢
- **FR-013**: 生成结果 MUST 在主流桌面浏览器中直接运行，用户无需安装、构建或配置任何环境
- **FR-014**: 用户 MUST 能在**无需注册登录**的前提下完成核心流程（生成、查看、迭代）

*以下两项的形态与范围已确认（2026-09-15）：*

- **FR-015**: 生成结果 MUST 以**单个自包含页面**（页面结构 + 内联样式与脚本）的形态交付，使用户无需任何构建步骤即可看到可交互的结果。若 P1–P3 稳定后时间仍有余量，可评估升级为多文件工程形态，但 MUST NOT 以牺牲既有功能的稳定性为代价
- **FR-016**: 数据持久化 MUST 覆盖**平台自身**——项目、生成结果、对话记录。生成的应用持久化其自身业务数据（如记账应用中记录的一笔账）**作为延展能力**，在 P1–P3 稳定且时间允许时纳入；未纳入时 MUST NOT 影响平台自身持久化的完整性

### Key Entities *(include if feature involves data)*

- **项目（Project）**: 用户围绕一个应用想法所展开的全部工作的载体。包含名称、创建与更新时间，以及该项目下的所有生成版本与对话记录。是用户视角下的主要组织单位。
- **生成版本（Version）**: 一次完整生成所产出的结果快照。包含该次的输入描述、产出的应用代码、以及生成时间与序号。同一项目下的多个版本构成演进历史。
- **对话消息（Message）**: 用户与系统之间的交互记录，分为用户提出的要求与系统给出的响应。承载"多轮迭代"的上下文。
- **生成步骤（Generation Step）**: 一次生成过程中所经历的阶段性环节及其状态。用于向用户呈现智能体的工作进展。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 用户从空白页面出发，在 **90 秒内**获得一个可交互的应用界面
- **SC-002**: 用户提交描述后 **3 秒内**看到首个可见反馈，全程无超过 5 秒的界面无响应状态
- **SC-003**: **100%** 的已保存项目在刷新页面或服务重启后可完整恢复，无数据丢失
- **SC-004**: 生成的界面元素可被用户直接操作并产生预期反馈，**不出现**静态占位或无效按钮
- **SC-005**: 生成结果**无法**访问或修改平台自身的数据与凭据（隔离性可被验证）
- **SC-006**: 首次使用的用户**无需任何说明文档**即可完成一次完整生成，核心流程不超过 3 步操作
- **SC-007**: 在生成失败或超时的情况下，用户已输入的内容保留率为 **100%**
- **SC-008**: 生成过程中，用户可感知到明确的工作进展（步骤状态更新或过程输出），**不出现**仅靠加载动画的等待体验

## Assumptions

- **目标用户与形态**：面向桌面浏览器的单用户产品原型，不做移动端适配，不做多用户协作
- **无账号体系**：核心流程不设注册登录，用户身份以浏览器会话为单位（简化取舍，将在说明文档中阐述理由）
- **生成能力边界**：生成结果面向轻量级、以界面交互和数据展示为主的应用，不适用于复杂业务系统、多端应用或需要外部服务集成的场景
- **生成结果为纯前端形态**：受浏览器内即时渲染这一交付方式约束，生成的应用不包含独立的后端服务
- **分期交付策略**：P1–P3 为必达范围。FR-015 的"多文件工程升级"与 FR-016 的"应用级持久化"同属**延展能力后备池**，两者共享同一份剩余时间预算，需在 P1–P3 稳定后择一推进，而非并行铺开——避免两个半成品
- **依赖外部模型服务**：系统运行依赖可用的第三方大模型接口，其可用性与响应速度构成平台的固有约束
- **演示规模**：预期并发用户数在个位数到数十量级，不针对高并发场景设计
- **评估场景**：本产品将被评审者以"打开链接、当场试用"的方式体验，因此**首次访问即可用**与**数据不为空**具有高优先级
- **不在本次范围内**：用户权限体系、多人协作、生成结果的代码导出、自定义域名、计费与配额管理
