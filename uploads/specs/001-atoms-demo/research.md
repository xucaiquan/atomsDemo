# Phase 0 Research: 智能体驱动的应用生成平台

**Feature**: `001-atoms-demo` | **Date**: 2026-09-15

本文件记录计划阶段的技术决策。每条采用 `决策 / 理由 / 备选` 结构。

---

## R1: 生成流水线形态

**决策**：**三阶段串行**智能体流水线——需求分析 → 结构设计 → 代码生成，每阶段独立调用一次 LLM。

**理由**：
- spec 的 P4 用户故事要求「看见智能体在工作」，单次调用无法呈现分阶段进展，会丢掉产品的核心体验差异
- 前两阶段输出短（各约 200-500 token），延迟低（各约 2-5 秒），能在生成早期就给用户真实反馈，直接服务于 SC-002
- 第三阶段承担主要输出（完整 HTML），是耗时的部分

**备选**：
- *单次调用直接出 HTML* —— 最快，但失去「智能体驱动」体验，且复杂需求下生成质量明显更差。被否。
- *并发多 Agent「赛马」* —— 成本 ×N 而延迟不降，且需要额外的结果评估与择优逻辑。6-8h 预算内不划算。被否。

## R2: 流式传输协议

**决策**：**SSE**（`text/event-stream`）over HTTP POST，自定义事件类型。

**理由**：
- 数据流是单向的（服务端 → 客户端），SSE 比 WebSocket 更贴合且实现更简单
- Nginx 对 SSE 只需 `proxy_buffering off`，配置成本极低
- 相比轮询，能满足 SC-002 要求的实时性且请求量小得多

**⚠️ 关键实现约束**：浏览器原生 `EventSource` **只支持 GET 且无法携带请求体**，而我们的生成接口需要提交 prompt。因此**前端必须使用 `fetch` + `ReadableStream` 手动解析 SSE 帧**，不能直接用 `EventSource`。

**备选**：WebSocket —— 双向能力在此场景用不上，且需要额外的连接管理与心跳。被否。

---

## R3: 沙箱隔离策略

**决策**：`<iframe srcdoc="..." sandbox="allow-scripts allow-forms">`，并向 srcdoc 注入 CSP meta。

**理由**：
- **不加 `allow-same-origin`** 是关键：此时 iframe 获得**不透明源（opaque origin）**，无法访问父页面 DOM、`localStorage`、`sessionStorage` 与 cookie。这直接满足 FR-010 与 SC-005
- ⚠️ **绝不可同时设置 `allow-same-origin` 与 `allow-scripts`** —— 那样生成内容可读取宿主凭据，等于自开后门。此约束须在代码中以常量固定，不提供动态覆盖入口
- 注入 CSP 阻断外联，兼顾「自包含」（FR-015）与防数据外泄：

  ```
  default-src 'none'; style-src 'unsafe-inline'; script-src 'unsafe-inline'; img-src data: blob:
  ```

- `allow-forms` 是务实妥协：生成的记账/表单类应用可能使用原生表单元素

**已知限制（需写入说明文档）**：不透明源下，生成的应用**无法使用 `localStorage`**。这与 FR-016 的分期决策一致——应用级持久化本就是延展项，且届时需走 `postMessage` 通道而非直接存储。

**备选**：将生成页面托管在独立域名 —— 更灵活，但需额外的路由、清理与配额机制。MVP 被否。

## R4: DeepSeek API 接入 ✅ 已于 2026-09-15 实测验证

**决策**：使用 **`deepseek-chat`**，OpenAI 兼容接口 `base_url = https://api.deepseek.com`，模型 ID 走配置而非硬编码。

**实测结果**（2026-09-15，使用项目 key 直连 `api.deepseek.com`）：

| 模型 ID | 响应中实际 `model` | 模式 | 单次生成耗时 | 输出情况 |
|---|---|---|---|---|
| **`deepseek-chat`** | `deepseek-flash` | **非思考** | **6.8 – 13.0 s** | 干净完整 HTML，流内 **0** 个 reasoning 帧 |
| `deepseek-flash` | `deepseek-flash` | **思考** | 12.0 s | ⚠️ **不可用**——8000 max_tokens 全被 reasoning 占满，`content` 为空 |
| `deepseek-v4-pro` | `deepseek-v4-pro` | 思考 | 24.3 s | 可用，2741 帧 reasoning + 2330 帧 content |

**四条关键结论**：

1. **`deepseek-chat` 仍可用**——它是遗留别名，**静默指向 `deepseek-flash` 的非思考模式**。`GET /models` 只返回 `deepseek-flash` 与 `deepseek-v4-pro`，**不返回 `deepseek-chat`**，但该 ID 调用成功。⚠️ **因此绝不能用 `/models` 列表判断可用性**，必须实际调用验证。
2. **`deepseek-flash` 直连不可用** ⚠️ —— 它是思考模型，`max_tokens` 会被 `reasoning_content` 吃光，`content` 返回空串。**这是一个极易踩中的坑**：直觉上"直接调最新模型名"反而会失败。
3. **产出质量验证通过**——生成结果以 `<!DOCTYPE html>` 开头、`</html>` 结尾、含 `<script>`、**无 markdown 围栏**；2422 帧解析 **0 失败**；单次产出约 8 KB / 8002 字符。
4. **进度反馈可用**——流式正常，实测首字节与整体时延均在预算内。

**修正后的模型配置**：

| 阶段 | 模型 | 理由 |
|---|---|---|
| 阶段 1 需求分析 | `deepseek-chat` | 非思考、快，输出短 |
| 阶段 2 结构设计 | `deepseek-chat` | 同上 |
| 阶段 3 代码生成 | `deepseek-chat` 起步；质量不足时切 `deepseek-v4-pro` | 实测 6.8–13 s 可产出完整应用 |

**三阶段延迟预算**：约 3 × 8 s ≈ **24 s**，远低于 SC-001 的 90 s 上限，**余量充足**。即使阶段 3 换成 `deepseek-v4-pro`（总耗时约 40 s）仍在预算内——这为质量升级留出了空间。

**⚠️ `max_tokens` 调整**：实测 8000 恰好够一个简单应用，复杂应用有截断风险。**建议代码生成阶段设为 16000**，其他阶段 2000 即可。

**备选**：接 OpenAI / 通义千问 —— 需要额外 key 与成本；用户已确定使用 DeepSeek。

## R5: 多轮迭代的上下文策略

**决策**：只回传**上一版 HTML + 本次新指令**，**不回传完整对话历史**。

**理由**：
- 生成的 HTML 通常 10-30KB（约 5-15K token），单版回传即可让模型在原有基础上改进
- 若回传全量历史，上下文随轮次线性膨胀，成本与时延持续恶化，最终触碰窗口上限
- 符合 FR-006「基于原有结果产出更新版本，而非重新开始」

**备选**：回传全量历史 —— 上下文无界增长。被否。

## R6: 生成结果提取策略

**决策**：**三级容错提取**，按序尝试：

1. 匹配 Markdown 围栏 ```` ```html ... ``` ````
2. 匹配首个 `<!DOCTYPE html>` 或 `<html` 至文末
3. 兜底：整体内容作为 HTML

**理由**：LLM 输出格式不稳定，即便在提示词中明确要求「只返回 HTML」，实际仍会偶发包裹说明文字或围栏。单一策略的失败率不可接受——**提取失败等于整个产品失效**。

**测试要求**：该模块（`html_extract.py`）设计为**纯函数**，须覆盖上述三条路径及畸形输入（空串、仅围栏无内容、未闭合标签）的单元测试。

## R7: 部署形态

**决策**：**Docker Compose** 单机编排（`nginx` + `api` + `mysql`），Nginx 终止 TLS 并直接托管 Vue 构建产物。

**理由**：
- 环境可复现，出问题可整体回滚
- Vue 静态产物由 Nginx 直接返回，FastAPI 只处理 `/api/*`，无跨域问题且静态资源不占用 Python 进程
- 单机编排在 2vCPU/4GB 上绰绰有余

**备选**：裸机 systemd + 手工安装 MySQL —— 上手更快，但环境不可复现，故障时难以回滚。被否。

## R8: 域名与 TLS 🔸 待用户确认

**建议决策**：购买低价域名（`.top` / `.xyz`，约 ¥10-30/年）并配置 Let's Encrypt 免费证书。

**理由**：
- 交付物是「**可测试的在线访问链接**」，评估维度含「可交付性」。域名 + HTTPS 的观感明显优于 `IP:端口`
- 部分浏览器 API（剪贴板、Service Worker 等）要求安全上下文（HTTPS）
- 额外成本约 30 分钟

**备选**：直接用 `IP:非标准端口` 访问 —— 零成本、立即可用，但**无 HTTPS**，观感较差。

**状态**：**待用户确认**。此决策不阻塞任务拆解——两种方案的代码完全相同，只是 Nginx 配置不同。

## R9: 数据库字符集与字段类型

**决策**：`utf8mb4` / `utf8mb4_0900_ai_ci` / InnoDB；生成结果列使用 `MEDIUMTEXT`。

**理由**：
- 用户描述与生成内容含 emoji 与多语言字符，`utf8mb4` 是必须的（`utf8` 三字节实现会截断 emoji）
- 生成 HTML 典型 10-50KB，`TEXT`（64KB 上限）存在溢出风险；`MEDIUMTEXT`（16MB）留足余量且成本可忽略
- InnoDB 提供事务与行级锁，是 MySQL 8 的默认且唯一合理选择

## R10: 失败路径与幂等性

**决策**：生成过程**先落库后执行**——提交时即创建一条 `status='pending'` 的版本记录，流式过程中更新，失败则置 `status='failed'` 并写入 `error`。

**理由**：
- 满足 FR-011「失败时不丢失用户已输入的描述」——prompt 在开始生成前已持久化
- 避免「生成到一半进程崩溃，用户什么都拿不回来」的最差体验
- 服务重启后可通过 `status='pending'` 识别中断的生成，便于清理

**并发约束（FR-012）**：同一项目下若已存在 `status='pending'` 的版本，拒绝新的生成请求并返回明确提示，避免重复消耗。
